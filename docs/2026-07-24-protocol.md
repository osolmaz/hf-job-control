# Control protocol

HF Job Control separates desired state from observed state. Operators write a
small control document, and workers publish status and receipts after acting on
it. Checkpoint bytes stay in a Hugging Face Bucket.

## Identity

A logical run keeps one `run_id` across retries and resumes. Each physical Hugging
Face Job gets a different `attempt_id` and server job ID. Launchers put both
client-controlled IDs in labels and environment variables.

The default logical ID uses the sortable UTC petname form
`YYYYMMDDHHmm-adjective-animal`.

## Desired state

The control dataset stores one current document per run:

```text
controls/<run_id>.json
```

The document follows [`control-v1.schema.json`](../schemas/control-v1.schema.json).
Each update increments `generation` and uses the current dataset revision as its
parent commit. A competing update must retry after reading the new generation.

`run` permits work. `pause` ends the physical attempt after a safe checkpoint,
and a later `run` may refer to that checkpoint through `resume_from`. `stop`
finishes the logical run cleanly. `abort` records failure and exits with a
nonzero status.

A worker accepts generation gaps because it may miss intermediate desired
states. Re-reading the same generation is normal and does not create another
receipt within one attempt.

The first physical launch also stores its canonical launch specification at:

```text
launch-specs/<run_id>.json
```

Later attempts must match this immutable document. A failed launch may leave
the registration in place, which is intentional because the logical run has
already claimed its execution contract.

## Observed state

The status dataset uses this layout by default:

```text
runs/<run_id>/status.json
runs/<run_id>/attempts/<attempt_id>/receipts/generation-<generation>.json
```

`status.json` follows [`run-status-v1.schema.json`](../schemas/run-status-v1.schema.json).
It reports the latest boundary, checkpoint, metrics, applied generation, and
physical attempt. Workers also record the built-in Hugging Face `JOB_ID` when
it is available. Receipts follow
[`applied-control-v1.schema.json`](../schemas/applied-control-v1.schema.json) and
are immutable.

The desired-state repository cannot prove that an action happened. Receipts and
observed status provide that evidence.

## Progress

An application can publish progress to its existing approved Bucket:

```text
operations/<run_id>/progress/current.json
operations/<run_id>/progress/snapshots/sha256-<snapshot-sha256>/progress.json
```

Snapshots follow
[`progress-v1.schema.json`](../schemas/progress-v1.schema.json). The mutable
pointer follows
[`progress-pointer-v1.schema.json`](../schemas/progress-pointer-v1.schema.json).
Before replacing the pointer, the reporter uploads and verifies an immutable
snapshot and an immutable sequence claim. Competing claims stop publication
instead of letting one worker overwrite another worker's progress.

Counts cannot move backward within one `plan_id`. A changed input, denominator,
unit, or method uses a new plan. Applications report committed facts, while
monitoring systems calculate rates and finish-time ranges. Progress does not
replace checkpoints, receipts, or final output manifests.

## Checkpoint bundle

A checkpoint uses the deterministic `.hfjob` v1 container:

```text
HFJOB1\n
<8-byte unsigned big-endian manifest length>
<canonical manifest JSON>
<payload bytes in manifest path order>
```

The manifest follows
[`checkpoint-manifest-v1.schema.json`](../schemas/checkpoint-manifest-v1.schema.json).
It identifies the run, attempt, frozen plan, safe boundary, predecessor,
adapter, and every payload path with its byte count and SHA-256. The adapter may
write zero or more payload files below its checkpoint directory.

The complete bundle is uploaded to a key with this form:

```text
<run_id>/checkpoints/sha256-<bundle-digest>/checkpoint.hfjob
```

The artifact reference records the Bucket ID, key, exact byte count, and bundle
SHA-256. Workers verify all four before reading the manifest. They then verify
every payload before calling the adapter. Python and TypeScript produce the same
bundle bytes for the shared fixture.

## Claims and pointer hints

Each committed sequence has an immutable attempt-specific claim:

```text
<run_id>/checkpoints/claims/sequence-<sequence>/<attempt_id>.json
```

Claims follow
[`checkpoint-claim-v1.schema.json`](../schemas/checkpoint-claim-v1.schema.json).
They link the checkpoint to its predecessor. Different checkpoint references
for one sequence stop recovery. The mutable `<run_id>/current.json` follows
[`checkpoint-pointer-v1.schema.json`](../schemas/checkpoint-pointer-v1.schema.json)
and is a startup hint only. Missing or stale pointer bytes cannot hide a claimed
checkpoint.

## Boundary order

A worker follows this order whenever it can safely stop:

1. Finish the current unit and calculate metrics.
2. Send metrics to optional sinks such as W&B.
3. Ask the adapter to write its checkpoint payload files.
4. Build, upload, and verify the checkpoint bundle.
5. Publish observed status with the checkpoint reference.
6. Resolve the control branch to one exact revision.
7. Read and validate control from that revision.
8. Publish the applied-control receipt.
9. Return the action to the job.

TypeScript applications that use `CheckpointCoordinator` publish and verify the
immutable sequence claim after step 4. They update the pointer hint next and may
publish application progress only after the claim succeeds.

The application finalizes its own outputs after the controller returns an exit
decision. It then calls `Controller.finish()` to publish the final state.

## Resume

`pause` leaves status in `paused` with a verified checkpoint reference. The
operator runs `hf-job-control resume`, which verifies the bundle and publishes
a new `run` generation. Exact and boundary adapters include the reference.
Restart adapters publish `run` without it and repeat from immutable inputs. An
unsupported adapter rejects pause with a failed decision and a rejection
receipt.

A new physical attempt starts from the same immutable launch specification.

At startup, the controller verifies the outer artifact and inner checkpoint
manifest. It checks the logical run ID and adapter identity before the adapter
restores application state. The controller writes the adapter's restore
evidence into a `resumed` receipt before new work begins.

The operator launches the new attempt separately from publishing `run`. This
two-step flow makes a failed launch visible and safely retryable. It also avoids
pretending that a Hub commit and a compute request can form one atomic operation.

## Failure behavior

A malformed current control causes a safe pause after the worker has published
its checkpoint. A control-store outage receives bounded retries before the same
safe pause behavior. Optional metric sinks may fail without blocking checkpoint
or control handling.

An artifact with the wrong Bucket, key digest, byte count, or SHA-256 is
rejected before restore. Adapter mismatches and unsupported resume modes are
also rejected.

Direct `hf jobs cancel` remains an emergency action because it may prevent the
next checkpoint and receipt from being written.
